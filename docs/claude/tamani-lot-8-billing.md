# Tamani — lot 8 (passes and SasPay)

## Tamani passes and SasPay (lot 8)

Prepaid passes bought through SasPay's hosted checkout ([plan](../../docs/superpowers/plans/2026-10-29-tamani-08-forfaits-saspay.md), spec §5.6, §5.7, §6.7); the porteur's decisions are listed under « Lot 8 » in the roadmap.

- **Grid** — `PLANS` ([plans.ts](../../frontend/src/lib/tamani/plans.ts)): `TRIAL` (3 days, 50 answers, one campaign, numbers and WhatsApp, no per-group links, no export, « Propulsé par Tamani »), the five `PASS_IDS` (`WEEK` 3 900 FCFA / 7 days / 150 answers, `TWO_WEEKS` 5 900 / 14 / 350, `MONTH` 9 900 / 30 / 1 000, `MONTH_PLUS` 14 900 / 30 / 2 500, `MONTH_MAX` 24 900 / 30 / 5 000), `UNLIMITED` on quote (granted by hand, lot 9) and `FREE`, which now means « Sans pass » (one campaign, new answers pending). No top-ups and no 12-month pass: another pass starts now and, while the pass in force still runs, keeps its unused answers. `marginOf` and its test keep every pass at 70 % margin or more under `MARGIN_ASSUMPTIONS` (6 % collection, 4.5 % payout, 0.25 FCFA per answer). In the sections above, « Free » reads « Sans pass » and « Pro and up » reads « any pass ».
- **Pass state** — `Subscription` holds the pass in force (migration `9c_passes`: `periodStart`, `currentPeriodEnd`, `graceUntil`, `responsesIncluded`). [subscription.ts](../../frontend/src/lib/server/tamani/subscription.ts): `effectivePlan(sub, now) → { plan, inGrace, endsAt }` (a paid pass keeps its features 3 days after its end, `GRACE_DAYS`; the trial has no grace), `trialPass(now)` (every new shop, `POST /api/shops`), `applyPurchase(current, pass, used, now)` (starts now; while the current pass still runs, `currentPeriodEnd > now`, it carries `included − used` and never ends before it; in grace or after, the unused answers are gone and the new pass starts from zero, porteur 2026-10-30). Shops made before lot 8 stay « Sans pass ».
- **Counted answers** — an answer counts in a pass once `Response.countedAt` is set; a pending one is `locked = true` with no `countedAt`. [quota.ts](../../frontend/src/lib/server/tamani/quota.ts): `passUsage` → `{ plan, used, included, endsAt, inGrace, pending }` (also `usage` in `GET /api/shops/me`), `shouldLockNewCompletion` under `quotaLock(orgId)`, `unlockPending(tx, org, now)` opens the oldest first up to the room left. `answersClosed`: on `FREE` or `TRIAL`, 1 000 completed answers in the calendar month (`RECORDED_CEILING`, pending included) close the popup (« Réponses fermées pour ce mois », `409 ANSWERS_CLOSED` for a new answer). A paid pass never closes.
- **SasPay client** — [payments/saspay.ts](../../frontend/src/lib/server/payments/saspay.ts): `getSaspay()` is `null` without `SASPAY_API_KEY`; `createCheckoutSession` (`fee_charge_mode: 'ADD_ON'`: the customer pays SasPay's fees on top, porteur 2026-10-29 — SasPay ignores the field anyway unless « Autoriser le choix du mode de frais par l'API » is on; `expires_at` one hour on, amounts through `toSaspayAmount`: `9900` → `"9900.00"`), `checkoutSessionStatus`, `verifyPayment`. Replies are enveloped `{ success, data, code }`. `SaspayError(status, code, retryable)` never carries SasPay's message. A 4xx, 429 included, goes through the kit's `CircuitBreaker` as a value, so only 5xx and network errors open it. Verify and status bodies are read with or without the `{ success, data }` envelope (the OpenAPI examples are flat). The return page asks every 3 s for 30 s, then every 10 s (`pollDelay`). Payment is offered only in `PAYMENT_COUNTRIES` (SN, CI, ML, BF, TG, BJ, NE, CM, GA, CG), in XOF or XAF; the other shops read « Bientôt disponible ».
- **Reconciliation** — [billing.ts](../../frontend/src/lib/server/tamani/billing.ts). `startCheckout` writes a kit `Order` (`provider 'saspay'`, `organizationId`, `offer`, `providerChargeId` = session id, `paymentUrl` = `checkout_url`), reuses a pending one for the same pass, and returns to `/app/abonnement/retour?achat=<orderId>`. `reconcileOrder(db, saspay, orderId, now)` reads the session status, then `GET /payments/{id}/verify/`, and calls `activateFromPayment` only on `SUCCESS` with the order's currency and amount. Activation runs once (`Order.activatedAt`) under `billingLock(orgId)` then `quotaLock(orgId)`: `applyPurchase`, `unlockPending`, then a `passActivated` bell per owner and admin (dedupeKey per order and user). Three triggers run it, none trusted alone: the return page (`GET …/billing/orders/[orderId]`, polled every 3 s for 2 min), the webhook's `after()`, and the `billing-verify` cron (`reconcilePendingOrders`: 10 per run, newest first, 48 h back; a 429, 401 or 403 stops the run). A session that can no longer be paid (`CANCELLED` or `EXPIRED` without a successful payment) closes the purchase as `FAILED`, so dead purchases leave the batch; a failed attempt on an open session leaves it pending, and an `EXPIRED` order that SasPay reports paid still activates. The outbox is not used (its dispatcher is protected).
- **Webhook** — `POST /api/webhooks/saspay` ([route.ts](../../frontend/src/app/api/webhooks/saspay/route.ts), provider [webhook/saspay.ts](../../frontend/src/lib/server/webhook/saspay.ts)) runs the protected `createWebhookHandler`: HMAC-SHA256 of `${timestamp}.` plus the raw body with `SASPAY_WEBHOOK_SECRET`, 300 s window, dedup in `WebhookLog`. Its body carries no session, so it is only a signal that wakes `reconcilePendingOrders`; `parsePayload` keeps only `event`, `data.id`, `data.status` and a digest, so the payer never reaches `WebhookLog`. `503 BILLING_NOT_CONFIGURED` without the secret.
- **Routes** — `GET /api/shops/[orgId]/billing` (`MEMBER`: pass, per-campaign answers, purchases, `paymentAvailable`), `POST …/billing/checkout` (`ADMIN`, `{ offer }` → `{ orderId, checkoutUrl }`), `GET …/billing/orders/[orderId]` (`MEMBER`, reconciles then answers `{ purchase }`). Codes: `400 OFFER_NOT_BUYABLE`, `409 PAYMENT_COUNTRY_UNAVAILABLE`, `503 BILLING_NOT_CONFIGURED`, `503 PAYMENT_PROVIDER_UNAVAILABLE`, `404 PURCHASE_NOT_FOUND`, `409 ANSWERS_CLOSED`.
- **Crons** — `billing-verify` (every 5 minutes through cron-job.org, once a day in `vercel.json`) and `subscription-renewals` (`0 8 * * *`, `runRenewals` in [renewals.ts](../../frontend/src/lib/server/tamani/renewals.ts)): the J-3 bell and email, the grace bell, the end-of-trial bell, each with a dedupeKey that includes the user, so a second run tells nobody twice. Passes never renew on their own. Both export `GET` (what Vercel Cron sends) and `POST`, like every cron route since lot 8.
- **Screens** — the words are in [billing-view.ts](../../frontend/src/lib/tamani/billing-view.ts) (`meterLine`, `meterTone` at 80 % and 100 %, `pendingLine`, `graceLine`, `offerCards`, `unlimitedCard`, `planFeatures` (each card's lines, read from `PLANS`, greyed out where the plan leaves them out), `FOR_WHO`, `BEST_VALUE = 'MONTH_MAX'` « Le meilleur prix par réponse », `returnState`, `passCta`). Kit: `PassMeter` (`role="meter"`, `data-tone`) and `OfferCard` (its `features`, porteur 2026-10-30: the benefits sit on each card, no separate list). `/app/abonnement` « Mon pass » (`BillingView`, `BillingScreen`) and its return page (`ReturnView`, `ReturnScreen`); `ShellBanners` in `AppShell` (grace, pending answers), hidden on those two pages; the home and the sidebar carry the meter. Only an `OWNER` or `ADMIN` gets « Choisir ». The Illimité's « Contacter le support » waits for `LANDING_LINKS.whatsappContact`. [no-old-plan-words.test.ts](../../frontend/src/lib/server/observability/no-old-plan-words.test.ts) refuses « Pro », « Gratuit » and `/app/plus#forfait` in the shop space.
- **Home page grid** — `Pricing` renders `pricingOffers()` ([landing.ts](../../frontend/src/lib/tamani/landing.ts): the trial, the five passes, the Illimité) as `OfferCard`s in `OfferRail` (CSS `scroll-snap`: one card and a half on a phone, four and two arrows from 1024 px; the arrows are its only client code), each with its `planFeatures` lines (the trial greys out the per-group links, the export and « Sans « Propulsé par Tamani » »), then « Mobile Money ou carte · Pas de renouvellement automatique · Campagnes illimitées ».
- **Live key** — the porteur's SasPay account has no test key, so development runs on `sk_live_`. Tests mock `fetch` and never read the key. Reading rates or opening an unpaid session moves no money; a real payment needs the porteur's explicit yes, on the smallest pass, paid to their own merchant account.
- **Recette through ngrok** — SasPay's return and webhook need a public HTTPS URL. From `frontend/`, run `next build` then `next start --port 3001` with `APP_URL` set to the ngrok domain (the return URL is read from it), and `ngrok http 3001` with `NGROK_AUTHTOKEN` read from `.env.local`, never printed (on Windows, use the Microsoft Store ngrok: Defender deletes the zip build). The porteur declares the webhook in SasPay's dashboard at `<ngrok URL>/api/webhooks/saspay`; its signing secret is shown once and goes into `SASPAY_WEBHOOK_SECRET`. Without it, the return page and `billing-verify` still activate a paid pass.
